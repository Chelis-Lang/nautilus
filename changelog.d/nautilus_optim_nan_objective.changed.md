All four `Nautilus.Optim` exports now report NaN when a NaN reaches them, which for two of them replaces a silently wrong answer. The module's documented contract was already "return the approximate minimizer (or NaN on failure)", so this makes the code match the book rather than changing what the book promises. Every guard in the module is a comparison and every comparison against NaN is false, so the interval decision `f(c) < f(d)` picked the same branch at every step whatever the objective: `golden_section_search` narrowed deterministically toward `hi` and returned `2.0` on `[-0.5, 2.0]` for an objective that is NaN everywhere, and `brent_minimize` returned `0.75`, neither with a NaN nor a trap. Each function was measured separately rather than treated as one class, and they did not behave alike. At `max_iters = 100` `golden_section_search` returned `2.0` by budget exhaustion and at `100000` it aborted the process under `chelis eval --file`, because its interval stops shrinking once `b - a` reaches f32 resolution near the bracket and the `f(c) == f(d)` stall guard is itself defeated by NaN; `brent_minimize` returned `0.75` at every budget, and aborted on a NaN bracket endpoint where `golden_section_search` returned NaN. `gradient_descent_1d` was already correct at every budget -- its `x_next - x_next != 0` check catches a NaN gradient on the first step -- and needed no change, so its test pins existing behaviour rather than fixing any. `newton_minimize_1d` looked correct at `max_iters = 100` and was not: a NaN first or second derivative reached NaN only by consuming the whole budget, which aborts the test worker at `100000`, and a NaN second derivative *at the converged point* fell through both the `< 0.01` and `<= 0` curvature rejections and returned the point as a verified minimum. Separately recorded and deliberately not addressed here: `f` is never applied in either `opt_gd_rec` or `opt_nmin_rec`, so the objective is a dead parameter of `gradient_descent_1d` and `newton_minimize_1d` -- the same discarded-argument shape as nautilus#80's `n_points`, but an API question rather than a NaN one. The guard tests `neq(x, x)` and not the module's own `x - x != 0` idiom in `opt_gd_rec`, which detects non-finite rather than NaN; the distinction was load-bearing in `Nautilus.Roots` and is kept consistent here. Fourteen tests were added, eleven of them red against the previous `src/optim.ch` -- six as assertion failures and five as stack-overflow aborts -- with two finite-objective controls and the `gradient_descent_1d` pin green on it. Signatures are unchanged, so the `stable` freeze in `SKILL.md` §6 holds for `golden_section_search`, `brent_minimize` and `gradient_descent_1d`. Found while fixing nautilus#114, whose body names `Nautilus.Optimize.minimize` -- a pass-through to `brent_minimize` -- as a reachable caller.
