`Nautilus.Optim` now reports NaN when a NaN reaches one of its four minimizers, which for three of them replaces a silently wrong answer. The module's book page already promised "the approximate minimizer (or NaN on failure)", so this makes the code match the book rather than changing what the book promises. The interval decision `f(c) < f(d)` is a comparison, and every ordering comparison against NaN is false, so that decision picked the same branch at every step whatever the objective: `golden_section_search` narrowed deterministically toward `hi` and returned `2.0` on `[-0.5, 2.0]` for an objective that is NaN everywhere, `brent_minimize` returned `0.75`, and `newton_minimize_1d` returned a point as a *verified* minimum when the second derivative at it was NaN -- falling through both the `< 0.01` and `<= 0` curvature rejections, which is the inverse of what that check exists for. Not every guard here is defeated that way: `opt_gd_rec`'s `x_next - x_next != 0` is a negated self-comparison and does fire on NaN, which is why `gradient_descent_1d` was already correct at every budget for a NaN gradient and is unchanged by this change. Each export was measured separately rather than treated as one class, and the four did not behave alike. `golden_section_search` returned `2.0` by budget exhaustion at `max_iters = 100` and aborted the process at `100000`, because its interval stops shrinking once `b - a` reaches f32 resolution near the bracket -- the stall is at width `1.1920929e-7` against `tol = 1e-7` -- and the `f(c) == f(d)` guard that catches that stall for a finite objective is itself defeated by NaN; `brent_minimize` returned `0.75` at every budget, because its parabolic path reaches the default branch with no guard to fall through. On a NaN bracket endpoint at `max_iters = 100` `brent_minimize` aborted where `golden_section_search` returned NaN, but that contrast is budget-specific and does not survive: at `1000` and above both abort, including the `100000` the two bracket-endpoint tests use. `newton_minimize_1d` looked correct at `max_iters = 100` and was not, reaching NaN for a NaN derivative only by consuming the whole budget, which aborts the test worker at `100000`. Two consequences are recorded rather than fixed. First, `f` is never applied in either `opt_gd_rec` or `opt_nmin_rec`, so the objective is a dead parameter of `gradient_descent_1d` and `newton_minimize_1d` and that is also why a NaN objective cannot reach them -- the same discarded-argument shape as nautilus#80's `n_points` on the same `stable` label, resolved there in #111 by rejecting rather than deleting, so the precedent exists; it is an API change and is tracked outside this change. Second, `newton_minimize_1d` returns `5.0` as a verified minimum of `(x-3)^2` when the second derivative is infinite rather than NaN, identically before and after, because `step = g/inf = 0` makes `x_next == x` before any curvature test runs. A NaN `tol` is deliberately **not** rejected: it only disables the width stopping condition, which is exactly what `tol = 0.0` does, and across two functions, four budgets and two objectives where the budget genuinely binds, NaN `tol`, `tol = 0.0` and `tol = 1e-6` are bit-identical in all sixteen cells on `origin/main`. Three tests pin that retained behaviour, including the `tol = 0.0` equivalence, so the decision is executable rather than asserted; the book says instead that a computed tolerance is the caller's to check. The guard tests `neq(x, x)` and not this module's own `x - x != 0`, which detects non-finite rather than NaN: `-inf` and `+inf` still carry a sign, the distinction is load-bearing in `Nautilus.Roots`, and the scalar predicate was verified NaN-only and IEEE-correct at NaN in the compiled lane as well as the evaluator. One behaviour change is a loss and is stated plainly: for an objective that is NaN on part of `[lo, hi]`, both bracketing methods now report NaN where they previously returned a number, and that number was an artefact of band placement rather than information. Measured on `origin/main` over three minimisers and four NaN-band positions, seven of twenty-four cells returned a point far from the true minimiser, always the edge of the band the method could not evaluate -- `3.6` for a minimum at `3.0`, `2.6` and `2.1` for a minimum at `1.5` -- so the cells that looked correct were the ones where the band happened to lie on the far side of the minimum. Because the two methods sample different points, one may now report NaN while the other converges; three tests pin both halves. Seventeen tests were added. Ten are red against `origin/main`'s `src/optim.ch` when each is run in isolation -- five as assertion failures and five as stack-overflow aborts -- and seven are green on it: the `gradient_descent_1d` pin, two finite-objective controls, the three NaN-`tol` retention tests, and the unreached-NaN-region test, all of which exist to pin behaviour this change does not alter. Four of the five aborts are red only because this workstation's worker stack overflows before the budget is consumed: the same calls at `max_iters = 100` return NaN on the unfixed code, so on a larger stack they would pass against it while still pinning the contract. Only the `golden_section_search` large-budget case is robustly red among the aborts. The baseline for all of this is `origin/main`, not this branch's first commit. Signatures are unchanged, so the `stable` freeze in `SKILL.md` §6 holds for `golden_section_search`, `brent_minimize` and `gradient_descent_1d`. Found while fixing nautilus#114, whose body names `Nautilus.Optimize.minimize` -- a pass-through to `brent_minimize` -- as a reachable caller.
