`Nautilus.Integrate.gauss_legendre_5` now rejects an unsupported `n_points` instead of silently answering with the 5-point rule. The argument was read once into a discarded binding, so the rule was always 5-point and a caller who passed `n_points = 20` expecting a 20-point rule received 5-point accuracy with no diagnostic; it now traps with `Nautilus.Integrate.gauss_legendre_5: n_points must be 5`. The guard is a checked pass-through on `half_range`, the block's first binding, so strict evaluation reaches it before `f` is applied at any node, including the midpoint node `x3 = mid` that no value of `half_range` moves; four of the five nodes do depend on it, which keeps the binding from being dead code. Five `tests_neg/integrate/` sidecars pin the rejection, the ordering in the uniform and midpoint cases, and a reachability control for each ordering claim. The signature is unchanged, so the `stable` freeze in `SKILL.md` §6 holds and no call site breaks: the only caller in the ecosystem, hello-chelis's `sin_integral_gl5`, already passes `5i64`, as does the `examples.json` sample in `Chelis-Lang/website`, and the exported signature including its `{}` effect row is byte-identical in the built `.chb`. The previous behaviour was documented -- both `SKILL.md` §6 and the book said `n_points` was ignored -- so this narrows a documented domain rather than correcting an undocumented accident, and the rows in both files are corrected here. The arity inconsistency nautilus#80 also names is deliberately not addressed: nautilus#104 holds that deleting the parameter would be the wrong fix because the parameter is the feature, which is the design position this change follows, and dropping it would additionally break a `stable` export on the published v0.7.47 that `Chelis-Lang/coral` pins.
